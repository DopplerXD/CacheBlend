# 第4章实验设计与分析

本章围绕第3章提出的基于查询感知的KV选择性重算方法展开实验验证，重点观察该方法在检索增强生成任务中能否在保持生成质量的同时降低首字延迟，并进一步分析不同重算比例对质量和效率折中的影响。和单纯比较最高得分不同，本文更关心方法在真实推理路径中的位置，也就是Query-aware相对于Full Reuse能否补回一部分质量，相对于Full Prefill又能否保留一定速度优势。

实验选取多跳问答和对话摘要两类任务，前者用于观察模型是否能根据当前查询从多个文档片段中定位相关证据，后者用于补充观察方法在较长生成任务中的表现。评价指标只保留生成质量、首字延迟、相对Full Prefill加速比和质量保真率四类，避免指标过多导致分析发散。根据实验统计结果，本文将qaw_ratio=0.6作为较优重算比例，该比例下Query-aware通常能保留较高质量，同时没有让TTFT过度接近完整预填充路径。

## 4.1实验环境

本实验在服务器主机上进行，GPU配置为RTX3090，显存为24G，CPU信息在实验日志中没有完整记录，本文不额外补写具体型号。软件层面上，主机所采用操作系统为Ubuntu22.04LTS，其余的软件版本和深度学习框架信息如表4.1所示。

本文实验基于CUDA推理环境完成，模型运行在约24GB显存的GPU设备上，软件环境使用Python3.10、PyTorch和Transformers框架。实验模型包括Yi-6B和Qwen2.5-1.5B两个开源因果语言模型，二者均使用bfloat16精度加载。Yi-6B参数规模更大，Prefill阶段的计算开销更明显，适合观察块级KV缓存复用在较大模型上的效果；Qwen2.5-1.5B推理速度更快，用于补充说明该方法在轻量模型上的可运行性。

实验环境保持一致，是为了让不同推理路径之间的差异主要来自KVCache处理方式，而不是来自硬件负载、模型精度或运行框架变化。本文并不把该原型系统和vLLM等工程化推理框架直接比较，也不讨论多用户并发场景下的吞吐表现，实验重点放在同一输入、同一模型下，Full Prefill、Full Reuse和Query-aware三条路径的相对变化。这样的设置虽然规模不大，但能较清楚地观察选择性重算是否带来了质量恢复，以及这种恢复需要付出多少首字延迟成本。

实验对比三种推理路径。Full Prefill是完整上下文推理路径，模型对完整Prompt执行预填充，可作为生成质量参照；Full Reuse是直接缓存复用路径，系统读取文本块KVCache并完成位置重定位和拼接，速度通常较快，但缺少当前查询带来的跨块上下文；Query-aware是本文方法，它先复用文本块缓存，再根据当前查询选择部分文本块Token进行重算，把新的KV写回复用缓存后继续生成。三种方法使用相同样本和模型设置，只改变KVCache的处理方式。

| 方法         | KV处理方式                  | 主要作用 |
| ------------ | --------------------------- | -------- |
| Full Prefill | 完整Prompt重新Prefill       | 质量参照 |
| Full Reuse   | 读取并拼接块级缓存          | 速度参照 |
| Query-aware  | 复用缓存后重算查询相关Token | 本文方法 |

表4-2三种推理路径设置

Query-aware的核心参数为qaw_ratio，它表示参与选择性重算的文本块Token比例。本文曲线实验中qaw_ratio从0到1变化，步长为0.05。比例较小时，重算Token少，推理速度更接近Full Reuse；比例较大时，重算内容增加，生成质量更容易接近Full Prefill，但TTFT也会随之上升。

这里需要说明，qaw_ratio不是越大越好。较高比例确实会让更多文本块Token被重新计算，但这些额外计算并不一定全部落在真正有用的位置上，尤其是当检索文本块中存在噪声段落或无关说明时，单纯增加重算比例可能只是在放大计算开销。本文把qaw_ratio作为一个可调参数，是希望找到一个能兼顾质量和首字响应速度的区间，而不是追求完整重算。

## 4.2实验数据集和评估指标

实验使用MuSiQue、2WikiMQA和SAMSum三个数据集。MuSiQue和2WikiMQA属于多跳问答任务，样本通常包含多个文档片段、一个当前问题和标准答案，模型需要把不同文本中的实体、事件或关系连接起来才能得到答案。SAMSum是对话摘要任务，输入为对话内容和参考摘要，模型需要生成较完整的摘要文本。三类数据放在同一组实验中，是为了观察查询感知选择性重算在短答案问答和摘要生成中的表现差异。

MuSiQue和2WikiMQA更贴近本文方法的主要使用场景，因为当前问题会比较明确地指向文档片段中的若干实体、关系或时间信息，查询感知Token选择可以借助这些线索判断哪些位置更值得重算。SAMSum的输入形式不同，它不一定围绕一个短问题展开，而是要求模型把一段对话压缩成摘要，所以它在本文中更多承担补充验证作用，用来观察该方法在生成目标更开放时是否仍能保持一定质量。

表4-3实验数据集与评价指标

| 数据集   | 任务类型 | 样本形式       | 样本数 | 输入字段                | 质量指标 |
| -------- | -------- | -------------- | -----: | ----------------------- | -------- |
| MuSiQue  | 多跳问答 | 预处理问答样本 |    150 | ctxs、question、answers | F1       |
| 2WikiMQA | 多跳问答 | 预处理问答样本 |    200 | ctxs、question、answers | F1       |
| SAMSum   | 对话摘要 | 预处理摘要样本 |    200 | context、input、answers | Rouge-L  |

对于MuSiQue和2WikiMQA，本文采用F1衡量预测答案和标准答案之间的Token重叠程度；对于SAMSum，本文采用Rouge-L衡量生成摘要与参考摘要之间的最长公共子序列相似度。两类指标取值越高，说明模型输出越接近参考结果，但F1和Rouge-L的含义不同，所以正文只在同一数据集内部比较不同推理路径。

F1更适合短答案问答任务，它能够反映预测答案是否包含标准答案中的关键Token。对于多跳问答来说，模型可能输出完整短语，也可能只输出实体名称，F1可以在一定程度上容忍这些表述差异。Rouge-L更适合摘要任务，它关注预测摘要和参考摘要之间的最长公共子序列，不要求两个句子完全一致。由于摘要任务的表达方式更灵活，Rouge-L只能作为近似评价指标，正文分析时不会把SAMSum结果和问答任务的F1直接混在一起解释。

TTFT表示首字延迟，即从请求开始到模型生成第一个Token所需要的时间。本文方法主要改变Prefill和Decode前的KV准备过程，TTFT能够比较直接地反映块级缓存复用和选择性重算对交互响应速度的影响。相对Full Prefill加速比用于衡量速度收益，计算方式为：

$$
Speedup=\frac{T_{FullPrefill}}{T_{Method}}
$$

其中，$T_{FullPrefill}$表示Full Prefill路径的时延，$T_{Method}$表示被比较方法的时延。Speedup大于1时，说明该方法相对Full Prefill具有速度优势。质量保真率用于衡量Query-aware相对Full Prefill保留了多少生成质量，计算方式为：

$$
Retention=\frac{S_{QueryAware}}{S_{FullPrefill}}
$$

其中，$S_{QueryAware}$表示Query-aware的F1或Rouge-L得分，$S_{FullPrefill}$表示Full Prefill的对应质量得分。Retention越接近1，说明Query-aware越接近完整上下文推理的质量表现。

Speedup和Retention分别对应效率和质量两个侧面。只看Speedup时，Full Reuse往往会显得更好，因为它复用最多、重算最少；只看Retention时，高重算比例又更容易占优，因为更多Token被更新后，结果更接近Full Prefill。本文把两者放在一起使用，是为了避免结论偏向某一个单项指标。一个可接受的重算比例，应当在质量没有明显下降的同时，仍然保留一定首字延迟优势。

## 4.3实验结果与分析

图4-1展示了选定设置下三种方法在两种模型和三个数据集上的TTFT与质量关系。该图是本章结果分析的主要依据之一，横向可以看到不同数据集上的质量位置，纵向可以看到首字延迟差异。整体来看，Full Reuse通常位于较低TTFT区域，说明直接复用块级缓存确实能减少首字等待时间，但在质量上容易低于完整上下文推理；Full Prefill质量更稳定，但首字延迟较高；Query-aware大多位于二者之间，说明选择性重算能够用一部分额外计算换回一部分生成质量。

![图4-1选定设置下TTFT与质量对比](../../../../../Library/CloudStorage/OneDrive-cugb.edu.cn/1毕业设计/毕业论文/analyse/qaw_visualizations/figures/fig17_best_ratio_ttft_f1_grid.png)

图4-1选定设置下TTFT与质量对比

从图4-1可以看出，Query-aware在问答任务上更接近理想折中。对于2WikiMQA和MuSiQue，Query-aware的质量点通常明显高于Full Reuse，并向Full Prefill靠近，说明当前查询中的实体和关系信息能够为Token选择提供有效线索。它的TTFT虽然高于Full Reuse，但没有完全退化为Full Prefill，这正是选择性重算希望得到的状态。SAMSum中Query-aware也能恢复一定Rouge-L，但TTFT优势不如问答任务稳定，正文不再对其原因作过多展开，只把它作为摘要场景下的补充结果。

图4-1的意义在于，它把“质量”和“首字响应”放在同一张图里观察。若某个方法只在质量上接近Full Prefill，却在TTFT上也几乎等同于Full Prefill，那么它对交互式推理的价值就会变弱；若某个方法只保留了Full Reuse的低TTFT，却无法改善生成质量，那么它也不能解决直接复用带来的上下文损失。Query-aware位于两条基线之间，说明选择性重算确实带来了可调空间，系统可以根据任务需求在速度和质量之间选择更合适的位置。

图4-2进一步给出了选定设置下三种方法的质量柱状对比。相比散点图，它更直接地呈现了Query-aware在质量上的位置。可以看到，直接复用虽然速度快，但在多个设置下质量低于完整预填充；Query-aware经过查询相关Token重算后，质量明显向Full Prefill靠近，说明本文方法并不是简单增加计算，而是在复用缓存基础上对当前问题相关的KV状态进行了修正。

从质量柱状图来看，Query-aware的优势主要体现在相对Full Reuse的恢复上。Full Reuse把文本块当作独立缓存单元直接拼接使用，速度很快，但它没有把当前查询对文本块内部Token的影响重新写入KV状态。Query-aware在这一基础上只重算部分相关Token，虽然不能完全等价于完整Prompt计算，却能把一些与问题关系更紧密的位置重新更新。对于本科论文实验来说，这个结果已经能够说明方法思路是有效的：它不是为了替代Full Prefill的理论上限，而是为块级缓存复用提供一个更稳的修正环节。

![图4-2选定设置下质量得分对比](../../../../../Library/CloudStorage/OneDrive-cugb.edu.cn/1毕业设计/毕业论文/analyse/qaw_visualizations/figures/fig18_selected_setting_score_bars.png)

图4-2选定设置下质量得分对比

在Yi-6B对应的曲线实验中，qaw_ratio=0.6的表现较为稳定。MuSiQue上Full Reuse的F1为0.2205，Full Prefill为0.2429，Query-aware在qaw_ratio=0.6时达到0.2368，已经接近完整预填充；对应TTFT从Full Prefill的1.304s降到1.041s。2WikiMQA上Full Reuse的F1为0.2492，Full Prefill为0.2831，Query-aware达到0.2718，TTFT也低于Full Prefill。SAMSum上Query-aware的Rouge-L为0.1804，虽然距离Full Prefill的0.2078仍有差距，但相比Full Reuse的0.0707已经有较明显恢复。

这组结果可以更具体地说明qaw_ratio=0.6的折中含义。在MuSiQue和2WikiMQA上，Query-aware没有把所有文本块Token都重新计算，却已经恢复了相当一部分Full Reuse损失的质量；在TTFT上，它又没有像高比例重算那样完全贴近Full Prefill。也就是说，中等比例重算把计算预算集中到查询相关位置后，可以让模型在较短等待时间内获得更接近完整上下文的KV状态。SAMSum虽然质量恢复幅度也比较明显，但摘要任务的输出形式更开放，所以本文不把它作为选择比例的主要依据。

图4-3展示了Yi-6B下不同qaw_ratio对应的生成质量变化。随着重算比例从较低值逐步增加，Query-aware总体上能逐渐缩小和Full Prefill之间的距离，尤其在MuSiQue和2WikiMQA上更明显。这个现象说明，多跳问答中的查询文本对Token选择有实际帮助，适当比例的重算能够让模型重新利用当前问题相关的文档位置。比例继续增大时，质量不一定单调提升，说明仅靠提高重算数量并不能保证每个样本都变好。

质量曲线中出现波动是正常现象。选择性重算改变的是部分Token的KV状态，最终输出还会受到答案格式、分词粒度和解码时上下文状态的共同影响。某些比例下，更多Token被重算后反而可能引入新的局部不一致，所以曲线不会严格按照qaw_ratio上升。本文更关注整体趋势和可用区间，而不是把某个点上的偶然高分看作绝对最优。

图4-3Yi-6B下重算比例与质量关系

图4-4展示了Yi-6B下不同qaw_ratio对应的TTFT变化。Full Reuse通常具有最低TTFT，Full Prefill较高，Query-aware随重算比例增加逐渐向Full Prefill靠近。以MuSiQue为例，qaw_ratio=0.6时TTFT约为1.041s，仍低于Full Prefill的1.304s；qaw_ratio继续升高后，TTFT会更接近完整预填充路径。这个结果说明qaw_ratio直接控制了选择性重算的计算代价，比例过高会削弱缓存复用带来的响应优势。

TTFT曲线和质量曲线结合起来看，可以看到本文方法的主要限制也比较清楚。选择性重算并不是免费操作，被选中的Token越多，Packed Prefill和KV写回带来的额外计算越多。低比例时速度优势明显，但质量恢复有限；高比例时质量可能更接近Full Prefill，但首字延迟也会越来越高。qaw_ratio=0.6处在这两类趋势的中间区域，既不是最低延迟设置，也不是最高质量设置，但更适合作为默认折中点。

![图4-4Yi-6B下重算比例与TTFT关系](../../../../../Library/CloudStorage/OneDrive-cugb.edu.cn/1毕业设计/毕业论文/analyse/qaw_visualizations/figures/fig03_yi6b_speed_baseline_curves.png)

质量保真率和加速比可以把上述变化放到同一个判断框架中。根据qaw_ratio_scores.csv的统计，qaw_ratio=0.45时平均Retention约为0.819，平均Speedup约为1.145，速度更好但质量保持略低；qaw_ratio=0.75时平均Retention约为0.885，平均Speedup约为1.014，质量更高但速度优势接近耗尽；qaw_ratio=1.0时Retention升到约0.939，Speedup降到约0.927，说明过高比例已经可能慢于Full Prefill。qaw_ratio=0.6时平均Retention约为0.844，平均Speedup约为1.059，虽然不是单项指标最高，却在质量保持和速度收益之间更平衡。

综合图4-1到图4-5可以看出，本文方法的价值主要体现在可调折中上。Full Reuse速度快，但质量可能下降；Full Prefill质量完整，但首字延迟较高；Query-aware通过当前查询选择部分文本块Token进行重算，使结果落在两者之间。对于本文实验设置，qaw_ratio=0.6通常能够保留较高质量保真率，同时避免高比例重算带来的TTFT明显上升，所以本文将其作为较优重算比例。该结论并不表示0.6在所有任务上都是最优，而是说明在当前模型、数据和实验流程下，它能较好地体现查询感知选择性重算在生成质量和推理效率之间的平衡。
